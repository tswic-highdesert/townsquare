This section proves that, then writes down the rules that keep it true.

Adding is always safe

A new token nobody references yet cannot break anything. Ship it, document it, let components adopt it when they need it.

Changing a value is routine

Breaking the contract therefore requires editing that list on purpose, in a diff a reviewer can see, rather than by renaming a field in an object.

Do not touch
  • --ts-ink* and --ts-hairline. They are tuned for reading and they are why the type holds up at 4.4:1 in every town.
  • --ts-brick. One alarm register, shared across every town, so an emergency looks like an emergency to someone who moved here from Delta.
  • --ts-space-* and --ts-radius-*. Change these and creations built elsewhere stop lining up with your shell.
  • Component CSS. If you are editing a component to reskin, the reskin is wrong.
Your town in ten minutes
  1. 0:00 Fork the repo. Copy towns/harbor/ to towns/<yours>/.
  2. 1:00 Pick two colours you already own: one structural, one action. Paste them into --ts-navy and --ts-terracotta.
  3. 3:00 Run npm run tokens:check. It derives the alphas, the hover and the tint for you and reports every contrast pair.
  4. 5:00 Fix whatever it flagged. Usually this is darkening the action colour by one step.
  5. 7:00 Set place in town.json.
  6. 8:00 Open the sheet with ?town=<yours> and read the three screens above in your own palette.
  7. 10:00 Ship. No creation was touched, and no creation needs to be.

The recipe is short on purpose. A theming system that takes a week is a theming system nobody uses, and a town that cannot reskin in an afternoon will fork the components instead, which is the one outcome that kills the seam. The cost of that shortness is that some things are simply not themeable, and saying so plainly up front is kinder than letting a town discover it after they have already shipped.

Why this must run at build and not in review. The failing value does not stay in the shell. It is injected into every sandboxed creation on the next page load, so a town can break fifty apps it did not write and never see it, because the reviewer only ever looks at the shell.
The honest limits of the seam
  • Contrast is checkable, harmony is not. A town can pass every ratio and still look like a parking ticket. The tool says readable, not good.
  • A creation can hardcode. Nothing stops a builder writing #C4714E in their own CSS, and that creation will look wrong in Harbor forever. The MCP submission lints for hex literals and warns, it does not reject, because rejecting a working app over a colour is worse.
  • Photography does not theme. Every lead image in the three screens above is the same photograph. A cool-blue town running warm-golden local photos is a mismatch no token can fix.
  • Semantic drift. If a town sets --ts-sage to a red, every verified badge in every creation turns red and still means verified. The name survives, the meaning does not.
Semantic tokens, the layer this system is missing A component that asks for terracotta when it means "primary action" is describing a colour, not a role.

Today a button reaches for --ts-terracotta and a notice reaches for --ts-gold. That works while the palette and the roles line up, and it stops working the moment they do not. Harbor's action colour is a teal. It is still called terracotta in every creation in that town, and a builder reading the token list has to know the lore to understand why.

The fix is an alias layer on top of the raw palette. Raw tokens stay exactly as they are, keep their names, and keep resolving. Semantic tokens are added beside them and components migrate one at a time.

The migration cost, stated honestly
Additive

Nine new names, zero renames, zero removals. The pinned test grows by nine lines and nothing in it changes. Every existing creation keeps working because every raw token keeps existing.

Two names for one colour

The real cost. For a while both --ts-terracotta and --ts-action are valid and a builder has to be told which to prefer. Documentation, not engineering, and it is a smaller tax than the lore tax we pay now.

Never a rename

Raw tokens are not deprecated and are not scheduled for removal. They are the physical palette and there are legitimate uses for reaching at it directly. Semantics are the layer above, not a replacement.

Where it pays

The day a town wants a different action colour from its structural colour, or a dark mode, or an accessible high-contrast variant. Every one of those is a role change, and roles are the thing we currently cannot express.

Recommendation: do not ship this yet
  1. The one-dark-card rule collapses. Restraint in this product is expressed by having exactly one dark card per screen. On a dark screen that card has nothing to be darker than, so the featured creation and the navy nav stop being emphasis and become texture. That is not a colour problem, it is a hierarchy problem, and it needs a second emphasis mechanism designed before dark mode is worth having.
  2. Two of the five hues stop working. Gold at 14 percent alpha on a dark surface is a smudge, and brick on dark loses the alarm quality that is the entire reason brick exists. Both need dark-specific values, which means the override is not seven lines, it is closer to thirty.
  3. It doubles the reskin surface. Every town now has to pass the contrast check twice, and a town that only tests light will ship a broken dark mode to every creation in it.

If it does become a request, ship it as a town-level opt-in with its own contrast gate, never as a system preference we follow silently, because a town that has not tested dark should not be handed one.

Naming rules
  • Every published property starts --ts-. That prefix is the namespace a creation trusts, and nothing else may use it.
  • Kebab case, derived mechanically from the source object. terracottaHover becomes --ts-terracotta-hover.
  • A trailing number is an alpha percentage of the hue named before it: --ts-navy60 is navy at 60 percent.
  • Names describe the palette, not the layout. There is no --ts-card-padding, because padding belongs to a component and the component belongs to the shell.
The three breaking changes
  1. Renaming a token. Every creation using the old name loses its styling silently.
  2. Removing a token. Same failure, and no error is raised anywhere.
  3. Changing what a token means. The name still resolves, so nothing breaks visually, and every creation now says something false. Making --ts-sage a warning colour is worse than deleting it.

Everything else, including every value in every town, is routine. If you are unsure which side of the line you are on, the test at packages/tokens/src/index.test.ts is the answer: if your change edits that list, it is breaking.

The reason to be this strict about a colour list is that Town Square's value compounds with builders, not readers. A resident who ships a lake-level app in March is not on call. If a rename in June breaks it, nobody fixes it, the app quietly rots, and the next resident sees a graveyard and decides not to bother. The token contract is not a styling convenience, it is the promise that makes building here worth a Saturday.
